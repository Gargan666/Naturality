NATURALITY — PROJECT OPTIMIZATION PLAN
Source review: 18 October 2026

Scope and evidence
------------------
This is a working plan, not an FPS benchmark report. The original review covered
the production source inventory, entry points and feature registrations, with
deeper inspection of recurring rendering, meshing, lighting, simulation, search
and world-generation paths. It is not a line-by-line correctness audit of every
class. The inventory contained 300 production Java files (113 common, 187 client).
File sizes and counts were used to navigate, not to estimate performance.

Priorities below express likely opportunity and user relevance. Source inspection
establishes that work happens; current profiling must establish how much it costs.
Historical profiles are leads only: several relevant implementations have changed.
No new runtime profiling or game tests were performed for the original review.

Paths use M = src/main/java/naturality and C = src/client/java/naturality.
This plan describes the current working tree, including uncommitted changes.

Initial implementation status
-----------------------------
Implemented: conservative local light-placement invalidation (including failed
placements, ray endpoints and full-height roof/snow dependencies); exact-order skylight
perimeter iteration; dirty-row/column water-map filtering with the original float
accumulation order; allocation reduction in particle shelter queries; and early
termination of already-blocked wind escape checks. Frame cadence and geometry are
unchanged. Full GPU map uploads remain in place.

Next batch implemented: exact packed-nibble light-section merging with uniform
section shortcuts and independently owned outputs; bounded extraction-local water
surface/appearance lookups (including missing surfaces); reuse of identical
coplanar model intersections; and allocation-free, equivalent rim-noise hashing.
Model captures remain pose-specific, wake iteration/draw order is unchanged, and
flowing surfaces with different planes still use both original intersections.

Chunk-loading priority implemented: exact neighboring biome-color samples are
reused for one block tessellation in native/Fabric model rendering and fluid
vertices. The fixed 27-entry neighborhood is lazy, source/world/state/origin-bound
and discarded in finally-scoped renderer calls; oversized coordinates retain
direct sampling. Interpolation, rounding, geometry, shaders and alpha metadata
are unchanged. The bounded new-terrain/return diagnostic identified this repeated
mesh work alongside ocean density generation. Exact color equivalence was checked
against the pre-change algorithm; short sampled profiles support reduced tint
work but do not establish an FPS gain. Separate snow-wrapper own work from delegated
model work before optimizing its inclusive profile stacks.

Ocean sampler overhead now avoids rewriting unchanged land columns, precomputes
the fixed coastline-search distances in their original order, and reuses seeded
spire parameters in a bounded 256-cell cache per sampler/worker. Base heights and
generation contexts are not cached. Original random draw order and arithmetic
are retained. Bit-exact comparisons cover scalar/volume output, full and sparse
volumes, coast/island thresholds, seed variation, negative/world-border positions,
cache eviction and worker order. Closer stack inspection shows most sampled time
under OceanTerrain.sampleVolume belongs to delegated vanilla noise, not custom
ocean shaping. That vanilla graph remains unchanged; do not count inclusive ocean
stack samples as the mod's own CPU cost or promise a broad chunk-loading speedup.

The observations below describe the pre-optimization review. The initial batch
does not implement persistent merged-light caches, incremental light propagation,
model-capture caching, shader/pass rewrites or broad underwater terrain culling.
Those remain profiling-dependent follow-ups. Keep validation reports in build/;
do not interpret reduced algorithmic work as measured in-game FPS improvement.

Non-negotiable acceptance criteria
---------------------------------
* Preserve visual output, animation phase, pixel alignment, light occlusion,
  transparency ordering, sound behavior, simulation timing and gameplay results.
* Preserve recent water fixes: every face orientation joins; boat interiors stay
  dry; waterline splits, air pockets, ice, chunk fades, refraction foreground
  guards, directional fog and menu backgrounds remain correct.
* No lower particle counts, shorter ranges, reduced texture resolution, slower
  simulation, approximate collision, altered random sequences or delayed AI work
  disguised as optimization. Those require a separate behavior-change decision.
* Keep bounded caches with explicit world, chunk, block, configuration and resource
  invalidation. Never read mutable client-world state from mesh workers as a cache
  fallback. A cache miss must produce the original result safely.
* Keep implementations feature-owned and consolidated. Extract shared APIs only
  for demonstrated reuse; do not introduce a project-wide scheduling framework
  simply to optimize one loop.

1. GENERAL STRATEGY
-------------------
Measure independent kinds of slowdown before selecting a rewrite:

  Render CPU: extraction, collision queries, particle updates, geometry building.
  GPU: water masks/composites, clouds, translucency and full-screen effects.
  Chunk workers: terrain meshing and repeated light/tint/shape queries.
  Integrated server: ticks, pathfinding, environment checks and world generation.
  Memory: allocation rate, GC pauses, retained worlds and GPU/native resources.

Record median and p95/p99 frame time and server tick time, queue lengths, work
counts and allocation rate. Use asynchronous GPU timing where available; do not
add synchronous GPU readback or per-pixel logging. At a 60 FPS cap, stable FPS
alone cannot show an improvement: compare actual CPU/GPU work and missed frames.
Keep the F3 state identical between comparisons because the reported slowdown
changed when that overlay was toggled. Match seed, route, time, weather, settings,
resolution and warm-up. Separate cold loading from steady-state measurements.

Use short, bounded scenarios: stationary and moving water views; a snowy forest;
stationary/moving light sources; explored versus new terrain; a populated village;
clouds while looking up; Nether/End scenes; repeated preview-to-world transitions.
Avoid combining these into one large scenario that hides the responsible feature.

Implement in this order within each owner:
  a. Remove duplicate work without changing when results become visible.
  b. Reuse scratch storage and immutable results within a known lifetime.
  c. Narrow invalidation to the true dependency region.
  d. Incrementally update expensive results using exact original calculations.
  e. Consider larger algorithm changes only if measurements still justify them.

Compare one feature change at a time. Stop when its measured benefit is negligible
or complexity outweighs the saved work. Do not promise a percentage gain before
measurement. Distinguish reduced work from reduced visible latency.

2. LIGHTING AND MOVEMENT-DRIVEN CHUNK WORK — FIRST PRIORITY
---------------------------------------------------------
Owners: C/rendering/lighting/dynamic/DynamicLighting.java;
C/rendering/lighting/dynamic/FractionalLightField.java;
C/fluids/water/WaterVisuals.java, nested Skylight.

Observed:
* Dynamic lighting collects sources and resolves their placement before its
  scheduled-update early exit. It already detects unchanged fields and limits
  source count/range. Changed cells already invalidate nearby sections for AO.
* invalidate(BlockPos) clears every cached placement before checking whether the
  changed block is within a source's influence. Even distant edits clear it.
* Propagation rebuilds a collision-aware field with per-rebuild state caching.
* Water has a separate client skylight engine. Its nearest-column search loops
  through entire squares and rejects their interiors to visit successive rings.
  It admits up to four columns per tick. Its light-data accessor copies and merges
  all 4,096 light values when both vanilla and optical data are present.
* Full-lit section shortcuts and dirty-section deduplication already exist.

Plan:
1. Count collection, placement, propagation, merged-data requests and actual mesh
   rebuilds separately. Attribute section invalidations to their originating
   feature so an apparently cheap tick cannot hide expensive downstream meshing.
2. Restrict placement invalidation to geometry that can affect cached placements
   or active sources. Check unresolved placements and newly selected sources too;
   preserve the existing periodic refresh until invalidation is proven complete.
3. Iterate only the skylight ring perimeter in the same visitation order. This
   avoids rejected interior iterations without changing column admission timing.
   Consider a maintained frontier later, with chunk-arrival and camera updates.
4. Cache merged light sections only when BOTH light inputs have reliable revision
   tracking. Object identity is insufficient if a DataLayer mutates in place.
   Publish stable snapshots to workers and invalidate on unload/settings/world
   changes. If revisions cannot be tracked safely, retain recomputation.
5. Reuse propagation scratch buffers without mutating published fields; cache
   registry/config emission lookups with explicit live-setting invalidation.
6. Only if propagation remains dominant, prototype affected-region updates with
   exact overlapping-source maxima and correct removal/dimming propagation.

Validate: moving/removed/overlapping lights, item drops, solid occlusion, chunk
arrival/unload, server light packets, AO borders and water/cave skylight. Compare
light fields and rebuilt-section sets, not just screenshots. This is client work;
it can contend with an integrated server, but is not proof of server tick cost.

3. WATER, LAVA AND ENTITY/SURFACE INTERSECTIONS — FIRST PRIORITY
--------------------------------------------------------------
Owners: C/fluids/water/WaterComposite.java, WaterVisuals.java,
WaterIntersection.java, WaterShaders.java; C/fluids/shared/FluidGeometry.java;
C/api/geometry/ModelCapture.java; C/fluids/lava/LavaIntersection.java;
src/client/resources/assets/naturality/shaders/core/water_optics.fsh.

Observed:
* Water needs color/depth captures, a water geometry mask, a separate boat-mask
  pass and multiple composites. Above-water optics can sample 24 wet intervals.
* The 256x256 map already caches columns and refreshes a limited number of tiles.
  A changed map still runs the full radius-12 separable filter and full upload.
* Intersection extraction gathers nearby entities, captures posed model geometry,
  intersects it with fluid planes, and creates pixel-level rim/wake geometry.
  Limits already exist. Repeated geometry, temporary objects and string wake keys
  are candidates; capture cannot be cached across changing animation poses.
* Frame-shared fog values, vertex-side inverse projection, lazy face-boundary
  queries, clipped zero-strength shafts and far-water color-work avoidance have
  already been implemented. They are not new recommendations.

Plan:
1. Measure each capture, mask, composite, map update and model-intersection stage.
   Count captures, triangles, covered pixels, refreshed tiles and uploaded bytes.
2. Refilter only changed map regions expanded by the complete filter dependency
   radius. Preserve arithmetic/order and keep full-refresh fallback for recenter,
   invalidation or large edits. Upload dirty rectangles if the current API supports
   it efficiently; measure whether several small uploads cost more than one full.
3. Reuse exact frame-local model captures only for identical entity, pose, origin
   and render context. Reuse tile fluid/light/tint queries within that scope.
   Replace string wake keys and avoid temporary per-pixel vector collections.
   Share mechanics with lava only where their contracts actually match.
4. Profile a minimal mask vertex path that retains water material identity,
   deformation, flow, chunk fades and menu transforms but omits unused color work.
5. Skip passes only when their output is provably unnecessary. Do not infer this
   merely from camera immersion: above-water views and air pockets still need
   underwater information. Avoid visibility readbacks that stall the GPU.

Underwater terrain culling:
The existing far-water optimization reduces color shading but retains depth and
alpha. Full geometry removal is a later, higher-risk step. Invisible terrain can
still block refraction, silhouettes, masks or background fill. A whole-section
skip requires proof for every pixel and affected pass, including air pockets,
waterline splits, transparent neighbors and the refraction margin. First separate
color/depth dependencies and measure the remaining cost. Keep the depth path until
an equivalent replacement is demonstrated; apparent darkness alone is no proof.

Do not merge boat and water mask passes: their attachment formats differ, including
between classic transparency and OIT. Do not lower mask precision, ray steps or
render resolution as part of this preservation-focused plan.

Validate: above/below water, all six exposed face orientations, flowing slopes,
ice, boats with ripples/rims, air pockets, third person against walls, night vision,
biome borders, chunk arrival/fades and previews. Cover classic and OIT separately;
claim Sodium compatibility only after a Sodium-present run.

4. FOLIAGE, SNOW AND PARTICLE SHELTER — FIRST PRIORITY
----------------------------------------------------
Owners: M/blocks/snow/SnowGeometry.java; C/blocks/snow/SurfaceSnowModel.java;
M/systems/weather/wind/WindPush.java; C/systems/weather/wind/WindRendering.java;
C/systems/weather/framework/WeatherClient.java; wind mixins on both sides;
M/systems/weather/overworld/snow/WeatherSnow.java.

Observed:
* Snow geometry performs support/patch searches and voxel-shape decomposition.
  Scoped geometry caches exist. Snow can extend 32 blocks below its owner, and
  moving leaf caps retain faces that sway can expose.
* Wind already shares frame terms and caches collision shapes by pose/context.
* Particle wind calls openSkyExposure at individual particle positions. Sheltered
  positions may check 24 nearby sky samples and perform collision rays. Height and
  sky lookups are already cached during particle passes; rays remain a candidate.
  This is more consequential than only the once-per-tick audio listener query.
* Thaw already uses the ticking chunk; natural snowfall already has budgets.

Plan:
1. Measure snow mesh generation, wind collision and particle exposure independently.
2. Reuse support shapes and their decompositions within each mesh/collision query.
   Check cache hit rates before extending lifetimes; context-sensitive shapes must
   not become an unsafe global block-state cache.
3. Optimize exact shelter rays through shared immutable collision data and existing
   pass-local sky samples. Cache complete results only for identical origin and
   context. Sharing one answer for an entire block changes shelter near openings.
4. Remove repeated shader expressions only with output-equivalence verification.
   Retain quantized movement, attachment continuity and snow-cap geometry.
5. Optimize repeated weather eligibility/temperature queries at their exact tick
   and position scope. Keep random draws, accumulation and thaw timing unchanged.

Validate: sheltered/exposed particles at edges, wind extremes, leaf/plant contacts,
snow on moving and partial supports, chunk borders, snowfall and thaw. A denser
forest is useful for profiling, but not an excuse for an unbounded stress test.

5. WORLD GENERATION — HIGH PRIORITY WHEN ENTERING NEW TERRAIN
-----------------------------------------------------------
Owners: M/worldgen/overworld/ocean/OceanTerrain.java;
M/worldgen/end/terrain/EndTerrainDensity.java; other Overworld/End feature owners.

Observed:
* Ocean coastline sampling visits a 25x25 lattice with continental noise queries.
  Final coast-distance results have a bounded thread-local cache; fixed distances
  are precomputed without changing search order. Seeded spire parameters also have
  a bounded worker-local cache, independently of the current base height.
* Surface lookup can scan Y=128 down to -32. The volume path already reuses vanilla
  density output when its vertical coverage permits; fallback/scalar calls remain.
  Columns with zero ocean blend retain that output without a second density loop.
* Short route profiles are dominated by delegated vanilla noise within ocean
  sampleVolume stacks; inspect leaf/callsite costs before choosing further work.
* End generation already has bounded island/column caches.

Plan:
1. Separate vanilla generation, custom density and decoration costs per chunk.
2. If climate query costs justify it, memoize repeated continental lattice inputs
   with bounded seed-aware worker-local storage. Fixed offset distances and spire
   parameter reuse are implemented; preserve their exact arithmetic and draw order.
3. Reuse column/surface results only within equivalent generation contexts, and
   only where existing volume reuse does not already solve the cost.
4. Reduce repeated shape/state lookups and allocations in decoration while keeping
   random draw order, placement order and region write bounds identical.

Validate deterministic blocks, biomes, heights and structures across representative
seeds, boundaries and worker scheduling, including monument elevations/reloads.
No lower-resolution noise or changed terrain. Generation alone cannot explain lag
when revisiting fully generated terrain; profile that case independently.

6. VILLAGERS, FISHING SEARCHES AND OTHER SERVER AI — SCENE-DEPENDENT
-----------------------------------------------------------------
Owners: M/systems/villagerwork/professions/ProfessionWork.java, ButcherWork.java;
M/systems/villagerwork/shelter/VillagerSnowShelter.java;
M/systems/fishing/VillagerBobbers.java, nested FishingSpots.

Observed:
* Farm searches cover a 17x7x17 region, rank candidates and attempt paths. This is
  per search, not a claim that every villager scans it every tick.
* Snow shelter fallback covers 33x9x33 positions and may try up to 32 paths; it
  already has a search interval.
* Fishing surveys share a bounded per-level cache and budget their initial cell
  scan. Completing a survey runs finish() synchronously, including pool/shore and
  cast analysis. That completion work is not covered by the scan-cell budget.

Plan:
1. Count search starts, candidates, paths and completion time by profession.
2. Optimize fishing finalization first if it causes spikes: primitive collections,
   reused neighborhood results and spatial indexing of exact cast candidates.
3. Share static candidate discovery where villagers inspect the same terrain;
   invalidate for edits/unloads and retain individual reachability and inventory
   decisions. Preserve tie ordering and target choice.
4. Avoid redundant animal-pair checks without changing pairing order or eligibility.

Time-slicing finalization or staggering AI checks can change when jobs become
available. Treat that as a separate proposal if exact same-tick optimizations are
insufficient. Do not reduce brain/pathfinding rates as an invisible optimization.

7. CLOUDS, SKY AND OTHER GPU EFFECTS — SECOND PRIORITY
----------------------------------------------------
Owners: C/sky/shared/clouds/CloudLayerRenderer.java;
C/sky/overworld/sunbeams/SunBeams.java; C/sky/shared/aurora/;
C/rendering/glint/GlintContours.java; C/rendering/heatwaves/HeatWaves.java;
C/rendering/fog/EndFogComposite.java.

Observed:
* Cloud geometry is cached but rebuilt as relevant cells/settings change; layers
  and transparency passes can create substantial overdraw. Preview cloud coverage
  is intentionally much larger than normal coverage.
* Sun-flare visibility already has a bounded ray budget; aurora geometry is cached.
* Glint creates transient CPU/GPU buffers per batch. Heat waves already gate work
  and use periodic, palette-filtered source discovery. Several effects copy the
  scene at different points in the render order.

Plan:
1. Determine GPU fill cost versus CPU cloud rebuild cost with separate pass timings.
2. Pool glint staging/GPU buffers with frame-safe retirement and bounded capacities.
3. If cloud rebuilding dominates, prototype updated edge strips/chunks with the
   exact original transparency order and exposed caps. This is riskier than simple
   buffer reuse and must justify its added bookkeeping.
4. Reuse identical same-frame occlusion queries where camera/ray/layer data match.
5. Draw a render-pass dependency map before sharing any scene capture. Copies from
   different stages are not interchangeable even if their dimensions match.
6. Cull only provably zero-contribution cards/regions. Preserve layer count, cloud
   extent, flare rays, aurora coverage and all blend behavior.

Validate looking up, horizon views, day/night/rain, previews, transparency modes,
sleep transitions and resource reload. Do not call a capped non-reproduction proof
that a previously reported whole-computer freeze is resolved.

8. PROCEDURAL TEXTURES, BIOME TINT AND SMALL EFFECTS
--------------------------------------------------
Owners: C/fluids/shared/ProceduralFluids.java; C/blocks/fire/ProceduralFire.java;
C/rendering/biometint/BiomeTint.java; C/portals/; C/rendering/shadows/;
C/rendering/breaking/; C/effects/; particle feature owners.

Plan:
* Measure simulation, mip generation and uploads separately. Coalesce redundant
  uploads between rendered frames only if every simulation tick and its random
  sequence still runs, with final data available before every consumer.
* Implemented: cache identical biome source queries within one block tessellation,
  preserving interpolation, rounding, texture alignment and the neighboring-pixel
  color bound. Keep the cache local to that build; do not reuse across world edits,
  resources, source changes or chunk rebuilds.
* Portal glow already bounds tracked blocks/particles. Consider cached frame-edge
  topology with block-update invalidation in portal-heavy scenes; preserve particle
  replacement timing, opening progress and crossing geometry.
* Shadow textures and resource-generated palettes already have reuse. Prioritize
  repeated placement/extraction or allocation only if measured, not their startup
  generation. Keep fire support geometry and model-wrapper behavior intact.

These are generally follow-up opportunities, not grounds for rewriting every small
feature. Rare event visuals, sounds, item changes, settings screens and static
content registration stay lower priority unless profiling identifies a regression.

9. MOVEMENT, ROTATION AND COLLISION
---------------------------------
Owners: M/systems/swimming/; M/systems/rotation/PlayerRotation.java;
M/systems/gravity/EndGravity.java; matching client owners.

These contain repeated collision-shape queries, decompositions and swept tests.
If measured costs are material, reuse obstacle lists within one movement operation
and remove intermediate allocations. Preserve all iteration/tolerance semantics.
Do not reuse results across changed pose, movement, context-sensitive block state
or entity collisions. Do not replace rotated targeting or swept collision with a
coarse box. Validate wall sliding, low ceilings, banks, Riptide, gravity transitions,
breathing and camera handoff before considering any algorithm change.

10. PREVIEWS, MEMORY AND SHARED LIFECYCLES
----------------------------------------
Owners: C/ui/menus/previews/MenuPreview.java; M/api/worlds/DisposableWorlds.java;
feature-specific world caches and GPU resource owners.

Measure retained worlds, queued preview work, native images/buffers and GPU targets
across repeated menu/world/reload cycles. Increasing allocated heap alone is not
proof of a leak; distinguish live retained memory after cleanup from committed heap.
Reuse immutable preview resources only with explicit ownership. Cancellation and
stale-result rejection already exist: verify them rather than adding duplicate
mechanisms. Investigate avoidable work before cancelled requests reach generation.

Preserve server-identity cleanup, no-save policy through worker shutdown and safe
handoff to gameplay. Keep preview-specific oversized cloud work in its own profile.
Do not solve lifecycle problems by disabling the saved-world preview feature.

11. IMPLEMENTATION WAVES AND COMPLETION GATES
--------------------------------------------
Wave A: bounded instrumentation and matched baseline captures; then narrow dynamic
        placement invalidation and exact skylight perimeter iteration.
Wave B: measured light-data reuse, water dirty-region updates and frame-local
        intersection allocation/query reuse. Keep these as separate changes.
Wave C: particle shelter and snow geometry hot paths; ocean sampling for new-chunk
        spikes, or fishing/villager finalization for village tick spikes.
Wave D: glint buffers and cloud mesh reuse if GPU/CPU profiles justify them;
        procedural uploads, portal topology and lifecycle retention as indicated.
Deferred: partial light propagation, broad underwater terrain removal and render-
          pass restructuring. Require stronger equivalence evidence first.

Reorder waves when measurements disagree with the source-based hypothesis. Each
change needs: baseline cost, bounded implementation, invalidation contract,
focused correctness evidence, matched after measurement and a clear rollback.

Safety and validation:
* Do not run a second client alongside manual play. Use disposable worlds or an
  authorized offline copy, never the user's original save.
* Start at 854x480, 60 FPS and a small render distance; use a bounded heap, limited
  processors and an external timeout/resource watchdog. A proposed starting
  envelope is 3 GiB heap, four active processors, 240 seconds maximum and a 4.5 GiB
  process-memory stop. These limits reduce risk; they do not guarantee OS stability.
* Stop on rising memory, sustained stalls or graphics-driver trouble. Do not
  increase load just because a safe run does not reproduce a problem. Higher-
  resolution GPU comparisons need a separately bounded capture when safe.
* Keep tests local under src/gametest. Run only relevant authorized checks; request
  authorization for any new game test. Existing coverage is not permission for
  an entire suite. Pure logic equivalence checks can avoid a game launch.
* After Java/build changes, run the All-source warning audit and fix introduced or
  touched-code warnings. Validate production packaging with local tests disabled
  when build wiring changes. No such build/audit was needed for this plan alone.
* An assertion pass is not visual inspection. Compare controlled views for image
  regressions, plus numerical geometry/light/world checks where appropriate.

Recommended next implementation scope: use the bounded profiles to prioritize
remaining water intersection rasterization and falling-water particle work, then
the snow/shelter paths in Wave C. Persistent merged-light caching remains deferred
until revision tracking and measured request reuse justify it. The narrow Wave A
lighting changes, incremental CPU water filtering, packed light-section merging
and extraction-local water query/coplanar-intersection reuse are implemented;
do not repeat them. Keep timing/allocation evidence and equivalence reports in
build/optimization-wave-b rather than treating microbenchmark gains as FPS gains.
